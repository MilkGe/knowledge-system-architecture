# Knowledge System Architecture

一个以 AI 协作为核心的个人知识系统参考设计。

这套系统解决一个问题：**如何让 AI 在个人知识库中像协作者一样工作，而非像个搜索引擎。**

它不是一套"clone 即用"的 Obsidian 模板。它是架构设计、协作协议和自动化管线的完整参考——任何技术用户都可以按这份蓝图搭建自己的 AI 协作知识系统。

---

## 三层架构

系统的核心回答三个问题，每个问题对应一层：

```
信息怎么进入 → 采集层 (Capture)
知识单元怎么稳定存在 → 结构层 (Structure)
认知怎么逐渐成熟 → 演化层 (Evolution)
```

### 采集层：信息怎么进入

从外部来源（社交平台、浏览器、手动创建）提取内容，格式化后存入 Inbox。

支持平台：抖音、B站、小红书、微信公众号、微博、知乎、贴吧。

**核心原则**：采集层不思考。分类、判断、关联都不发生在这里。采集层只负责"拿到"和"初步格式化"。

```
收到 URL → 平台识别 → 元数据提取 →
  ├─ 视频类：下载音频 → ASR 转录 → 结构化 JSON
  ├─ 图文类：下载图片 → 视觉分析 → 结构化 JSON
  └─ 文章类：提取文本 → 格式化 → 结构化 JSON
  输出写入 Inbox
```

输出规范包括统一 YAML 元数据（source_url, platform, author, collected_at 等）、文件名规则、转录文本排版标准。

### 结构层：知识单元怎么稳定存在

基于 PARA 方法（Projects / Areas / Resources / Archive）组织的目录体系，配合 YAML 元数据、平级标签、wikilink 链接约定。

**核心原则**：结构最小集。YAML 只保留 type/status/created/updated 四个必填字段。标签不建层级。wikilink 是上下文引用，不是知识图谱。

```
01-Projects/    有具体目标和截止日期的工作项
02-Areas/       需要长期维护的知识领域
03-Resources/   可反复查阅的参考资料
04-Archive/     归档的已完成项目
00-Inbox/       采集层产出，等待处理
```

### 演化层：认知怎么逐渐成熟

知识从原材料到成熟认知的自然过程，通过状态标记和演化动作追踪，不强迫知识走固定协议。

**5 个状态**：raw（原始采集）→ seed（已初步处理）→ developed（已系统化整理）→ stable（已形成稳定认知）→ archived（已归档）

**养料消耗模型**：Inbox 笔记是基础养料（消耗品），加工后原始文件不保留。外源内容加工后删除，个人思考笔记加工后保留。多篇同主题内容可以合并为一篇，比任何单篇都更有价值。

**沉淀机制**：被频繁引用的笔记自然成熟；长期不用的笔记自动衰减。不需要 AI 推导来"生成深度"。

### 为什么是三层

这个系统最初是五层架构（采集 / 结构 / 标注 / 流转 / 治理）。经过实际使用后发现：标注本质是结构的一部分，流转层过于形式化，治理是策略配置而非架构层。精简为三层后，每层解决一个根本问题，没有一层是多余的。（详见 `docs/architecture/design-decisions.md`）

## AI 协作协议

系统的核心差异化在于定义了 AI 的行为边界，而非让 AI 自由发挥。

### 三级权限

AI 在执行任何操作前，先判断操作级别：

| 级别 | 含义 | 典型操作 |
|------|------|---------|
| **Tier 3** | 自动执行，无需确认 | 读取文件、搜索、格式化修复 |
| **Tier 2** | 执行后通知用户 | 写入 YAML、建议标签、更新索引 |
| **Tier 1** | 必须用户确认 | 创建笔记、删除文件、合并内容、修改系统配置 |

### 信号判断

AI 在对话中收到的输入不全是"任务指令"。系统定义了信号强度判断：偶发问题直接修复，重复问题记录观察，系统性问题上升处理。

不是每次问题都需要上升到系统层面修改——维护成本必须纳入评估。

### Agent 路由

不同维度的任务交由专门的 AI Agent 处理：分类代理判断 PARA 归属，Inbox 处理代理批量加工笔记，Vault 诊断代理健康检查等。（详见 `docs/collaboration/`）

## 采集管线

`pipeline/` 目录包含了可独立运行的采集代码，实现从 URL 到结构化 JSON 的全自动处理。

```
receive_url.py           URL → 平台识别 → 下载 → 转录 → JSON
transcribe_sensevoice.py  SenseVoice 转录引擎（阿里通义，中文优化）
requirements.txt          Python 依赖
.env.example              环境变量模板
media-crawler-setup.md    MediaCrawler 可选集成指南
```

**核心依赖**：Python 3.11+, ffmpeg, yt-dlp, SenseVoice（首次运行自动下载模型 ~200MB）

**转录引擎**默认使用 SenseVoice-Small，比 Whisper 快 10-20 倍，中文转录质量更优。

**MediaCrawler** 作为可选后端提供增强的元数据采集能力。（详见 `pipeline/README.md`）

## 设计哲学

这个系统的设计基于以下判断：

- **知识系统的本质问题是三个**，一个层解决一个，不多不少
- **AI 的角色不是执行器，是协作者**——它需要知道什么能做、什么需要问、什么时候该停止上升
- **不需要概念对象体系**——文件就是原子单位，概念通过 wikilink 和标签隐式表达
- **认知是不规则的**——系统不强迫知识走固定协议，只提供状态标记和演化动作
- **笔记应该读起来像自己写的**——外源内容的来源痕迹在加工后可删除
- **规范是实际运行出来的**——过时的规范应该重写而不是修补
