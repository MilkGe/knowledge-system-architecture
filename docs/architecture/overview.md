# 三层架构总览

这个知识系统围绕三个根本问题构建：

```
信息怎么进入      →     知识单元怎么稳定存在      →     认知怎么逐渐成熟
     ↓                        ↓                           ↓
  采集层                   结构层                      演化层
```

系统不做多余的事。每个层回答自己的核心问题，不越界。

## 三层定义

### 采集层 (Capture)

**核心问题**：信息从外部世界进入系统的全部渠道和预处理。

- 多平台输入（社交媒体、浏览器、手动创建）
- 内容提取和格式化（结构化元数据、转录）
- 输出到 Inbox，不做分类、标签、价值判断

**关键原则**：采集层不思考。分类、关联、加工都不发生在这里。采集层只负责"拿到"和"初步格式化"。

### 结构层 (Structure)

**核心问题**：知识单元如何稳定存在。

- 目录体系（PARA 四分类：Projects / Areas / Resources / Archive）
- 元数据（YAML frontmatter：type / status / created / updated）
- 标签（平级结构，每篇 1-3 个）
- 链接（wikilink：上下文引用，不是知识图谱）

**关键原则**：结构服务于逻辑，不服务于形式。YAML 保持最小集，wikilink 不需要语义分类，标签不建层级。

### 演化层 (Evolution)

**核心问题**：知识怎么逐渐成熟。

- 状态标记（raw → seed → developed → stable → archived）
- 演化动作（collect / refine / connect / distill / apply / archive）
- 基于使用的沉淀信号（引用次数、编辑频率）
- 养料消耗模型（Inbox 是消耗品，加工后不保留原始文件）

**关键原则**：认知是不规则的。系统不强迫知识走固定协议，只提供状态标记和演化动作，让知识按实际使用自然成熟。

## 系统边界

- **文件 = 知识对象**。没有独立于文件的概念对象体系。概念通过 wikilink、标签、正文中的定义来表达，不是通过独立的抽象实体。
- **wikilink = 上下文引用**，不是知识图谱。绝大多数链接只需要表达"这篇和那篇有关"，不需要关系类型、方向、权重。
- **策略不是架构层**。权限、命名规范、协作协议等是系统策略配置，不是架构层的一部分。

## 架构与策略的分界

```
架构层                                 策略配置
─────────                             ────────
采集层 / 结构层 / 演化层              权限分级（Tier 边界）
                                       命名规范
                                       协作协议
                                       系统状态追踪
```

架构层回答"系统由什么构成"；策略配置回答"系统怎么运行"。策略可以随使用习惯调整，不改变架构层的定义。

## 为什么是三层

这个系统最初是五层架构（采集/结构/标注/流转/治理）。经过实际使用后发现：

- 标注（YAML、标签、wikilink）本质是文件结构的一部分，不是独立的一层
- 流转（知识在状态间的移动）过于形式化——认知的演化不需要复杂的状态机
- 治理是策略配置，不是架构层

精简为三层后，每层解决一个根本问题，没有一层是多余的。详见 `design-decisions.md`。
